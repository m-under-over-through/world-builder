# 0013. Privacy in one place, and the way back

Date: 2026-11-03. Status: accepted.

## Context

On 2 November 2026 Marco tried the whole app on staging for the first time. His notes, in his words: "repeating privacy privacy privacy everywhere almost results in the opposite. As I open the URL I immediately got very nervous this was some kind of creepy spying app. I think we should keep the app the way it is built but minimize privacy theater to a single info page." On the session end: "'That is a session' and the rest of the content on that page is very surreal." On the code: "The code-to-resume thing still seems highly complicated and likely most users will not understand it or forget to copy the code." On return visits: "I just suspect people will open it once and then forget at all about it"; he asked for a calendar reminder alongside the partner's newsletter.

The architecture plan (section 13) prescribes a privacy panel one tap from every screen and a trust page of seven numbered sections, and the screen map had a "Your privacy" button in the header of every screen, three links in the foot of every screen, and a session end in three steps that said the same thing three times. Everything the plan asks for stays true; this record changes where it lives and how it reads.

## Decision

**One page about the app.** The privacy panel, the trust page, the code and "delete me" are sections of one page, "About this app", reached from one small link at the foot of every screen (`apps/web/src/screens/About.svelte`). The header is the workshop's name and nothing else. The page, in this order: what this is, in two sentences; how answers are protected (the trust page's six paragraphs, without their numbered headings and without "your controls", which the page itself now is); your code, in one sentence, shown plainly with Copy; the facts the panel showed, read from the running app, as a plain list of label and value (cookies, hosts, permissions, the key, what the server holds with every row on request, the last sync, what waits, the last error, the version); "delete everything I sent", in two steps; and at the end the terms and the privacy policy. The caveat stays under the facts: the numbers come from the same app that makes the claims.

**The addresses stay.** `/<slug>/about` is the page. `/<slug>/panel` and `/<slug>/trust` still work, because a newsletter may carry them: they open the same page, scrolled to the facts and to "how answers are protected". `/terms` and `/privacy` open the two texts as before, and Back from them returns to the page when they were opened from it.

**Delete-me is two taps from any screen.** The foot of every screen (the welcome, the intro, the code field, the demo card, the card, the session end, the closed screen) carries the link; the page carries the button; the third tap is the confirmation. The two texts, the terms and the privacy policy, carry Back and no foot: opened directly by their address, they are three taps away. Nothing moved further away: before, the panel was one tap and the button on it the second. The glossary's "one tap away" for the privacy panel becomes "one link at the foot of every screen"; a glossary line is proposed in the build log.

**The code is shown, not masked.** The masked dots with "Reveal" were a second thing to understand about a thing that is already hard to understand. The page and the session end show the sixteen digits in four groups with one button, Copy. A code read over someone's shoulder lets that person continue a stranger's session or delete it; that was true with the mask too, one tap later. Shoulder surfing is not in the threat model of a reflection exercise on a phone; forgetting the code is.

**A plain session end.** One heading, "Thank you", and nothing said twice. The first session: the code in one sentence ("If you ever want to continue on another phone, this is you: [code]") with Copy; then the install offer where it is due; then "the next cards wait for you another day" with the reminder. Every later session: the heading, that line once, the reminder. The line about answers waiting to sync shows only while something waits; "everything is synced" is gone, since nothing is the quiet case.

**The install offer, once, on both platforms.** It is shown at the end of the first session only, under the code, as a note with the steps for this platform, easy to skip because nothing has to be tapped. Nothing is stored about it. On Android the installed app continues where Chrome was, since they share storage. On an iPhone a home-screen app has its own storage and starts without the code (ADR 0012's install note; `docs/learn/10-the-installed-app.md`), so the offer there says what it is: "a way back without the newsletter; the app asks for your code once." It is worth offering even so. Safari deletes everything a site stored after seven days of Safari use without a visit to the site, and a home-screen app is exempt from that rule: it is the one way an iPhone keeps a participant for the three weeks of a workshop. If Marco decides to drop the offer on iPhone, `installDue` in `apps/web/src/lib/install.ts` takes the platform.

**A calendar reminder.** "Remind me" at the session end opens `/<slug>/reminder.ics`, a file in the iCalendar format (RFC 5545) that the phone's own calendar reads: one event, twice a week on Wednesday and Sunday at 18:00 in the phone's own time, repeating from the day after the workshop opens until its close day, with an alarm at the time of the event, and the workshop's home address as the one link in it. The file is written into the build, one per workshop folder, by the same plugin pattern that writes the manifests (`apps/web/pwa.ts`), from the workshop's days and the words of the "Reminder" block in its copy; the absolute address comes from Netlify's build environment (`URL` in production, `DEPLOY_PRIME_URL` on a branch or a preview), with the development server's address as the fallback. Netlify serves it with `Content-Type: text/calendar` (`apps/web/public/_headers`); the service worker keeps it with the client's files and never answers a tap on it with the client's page. No service, nothing stored on our side, nothing about the person in it: the same bytes go to everyone, and the file never carries the code, a wave or an invite. The format is written by hand in `apps/web/src/lib/reminder.ts`, sixty lines with the RFC's sections named, rather than through a library.

## Consequences

- Privacy is said once, in one place, in full. A participant who never opens the page sees the workshop's name, the cards, and a small link. One who does finds everything the plan promised, in the order the brief named.
- The privacy panel and the trust page stop being screens of their own and become sections; the glossary words still name those sections. Two components are gone (`PrivacyPanel.svelte`, `Trust.svelte`), one came (`About.svelte`). The copy blocks "Trust page headings", "Trust page: your controls" and "Data management plan" are gone from `copy.md`; the plan's facts are said once in "who, where, until when". The terms and the policy in `copy.md` point at "About this app" instead of "Your privacy"; `docs/participant-texts.md`, which the legal review reads, still says "Your privacy" and is the integrator's to align.
- The code is one tap more exposed on the page and one tap less work to keep. The session end has no steps and no "Next": the install offer and the reminder are read, not walked through, and the install dismiss count is gone with them.
- The reminder is a file, so it cannot know when a participant's first session was: the series starts the day after the workshop opens, and a participant who adds it later sees earlier dates in the past, which never ring. A file built on the device would know the day, but a `blob:` address does not open the add-to-calendar sheet on an iPhone the way a `text/calendar` address on our origin does, and the file would then be the one thing the service worker could not keep.
- The weekdays and the hour are two constants. Marco changes them without a decision record; the test reads them back from the file.

## Alternatives not taken

- **Keep the header button, soften the words.** The button is the thing that says "privacy" before anything else on every screen; softer words on it still say it first.
- **A separate page for the code.** The code is one sentence; a page for it would make it look like a password.
- **Dismissals counted across sessions for the install offer** (the earlier rule: never after two "Not now"). An offer read as a note needs no "Not now", and a note shown once is shown once.
- **The install offer dropped on iPhone**, because the installed app starts without the code. Safari's seven-day rule makes the home-screen app the only durable home on an iPhone; the offer stays, and says what it asks. Marco's call to drop it remains open.
- **A reminder through a service** (a calendar API, a push subscription, a mail). Each is a vendor, an address of the person, or both. A file is none of those.
- **A `webcal:` link or a Google Calendar link.** `webcal:` asks the phone to subscribe to a feed, which some calendars poll from our origin forever; a Google link sends the person to Google. A plain `.ics` on our origin is added once and forgotten.
