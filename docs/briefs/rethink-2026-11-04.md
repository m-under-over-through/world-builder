# The experience, rethought: no code, no end of session, no install offer

A plan, 4 November 2026, late. Nothing in it is built. Written for Marco and the partner after Marco's test of the card screen on his iPhone, from his four points and one scare. Marco's answers of the same night are marked **Decided**.

## What Marco asked for

1. No limit of four cards at a time. A participant goes on as long as they want and stops when they want.
2. Resume where they left off, with no code. The code is scary and hard to understand. When Marco typed it, iOS offered his credit card number as autofill: a 16-digit numeric field looks like a card field, and in a creative workshop that looks like phishing.
3. No "add to your home screen" offer. People stay in the browser, keep the tab, or open the link again.
4. A link of their own per participant, so that opening the link from the email lands them where they left off. Less private than today, accepted, as long as the server never holds a name with an answer.

## What stays

The guarantee Marco restated: the server never holds a name next to an answer, answers are sealed on the device and the server holds envelopes only, nothing leaves the one origin, the export at the end is a spreadsheet without names. The deck engine's rules (warm-ups then checkpoints, set aside, deferred first next time). The design and the card screen as built. The readable copies on the device (ADR 0014).

## 1. Rounds instead of sessions, and no end screen

Today a session is four cards (three warm-ups, one checkpoint, from `workshop.json`); the fourth card ends it with "Thank you", the code, the install offer and "Remind me".

Proposal: a session becomes a round, invisible. When a round's queue is done the next round starts at once, with a new seed and the deferred cards first, as the engine already plans it. No screen between rounds; the stack simply goes on. Stopping is closing the tab; the next open resumes the same card, by the replay that exists. The only end is the deck's: when every card is answered, a short "That is every card" screen, and the world. "Remind me" moves to the foot of "Your world so far" and to the about page. The toast "Set aside for another day" becomes "Set aside for later".

What changes: the client only (`lib/state.svelte.ts`: start the next round where the session end was; the session-end screen goes; the install offer goes with it), the copy blocks, the screen map, one decision record. The engine, the events, the sync and the export do not change: rounds are sessions in the database, numbered as before. A participant can go through all 42 cards in one evening; that is the point.

## 2 and 4. Who you are, without a code

The code exists because the server must tell participants apart without a name, and because a device forgets: an iPhone deletes a site's storage after seven days of Safari use without a visit, and a home-screen app has storage of its own. Two paths replace typing it. Both end the 16-digit field and its autofill.

**Path A, the link is yours.** The newsletter carries, for each recipient, a value of its own in the link, after the `#`: `https://worldbuilder.under-over-through.co/rural-manufacturing/join/wave-1#p=<value>`. What follows `#` never leaves the browser: it is not sent to Netlify, not to the API, not written in any log, not passed on as a referrer. The client turns the value into the 16-digit code by a one-way hash and joins as today; the server sees exactly what it sees now, a keyed hash of a code. A second device opening the same link gets the same code: the join answers "taken", and the client reads that as "this is me" and continues, intro already seen. A link without a value (a forwarded mail without it, a copied address) makes the device its own code, silently, as today. That is Marco's point 4 as asked: open the email, continue, on any device.

What it costs. The guarantee changes from "nobody can attribute an answer" to "no single party can": the newsletter tool holds which value went to which email address, for the partner; our database holds the hashed value and the sealed answers, for Marco; attribution would need both, plus the pepper. The consent text, the privacy policy and the trust page must say so, and they are under legal review this week. The partner's newsletter tool must be able to put a per-recipient value into a link and must not strip the `#` part through its click tracking; a test send decides that before anything is built. A forwarded email forwards the identity; invites remain the way to bring someone in.

**Path B, one cookie.** The API sets a cookie at join: `HttpOnly`, `Secure`, `SameSite=Strict`, a random secret, nothing else, kept for the workshop's weeks. Safari's seven-day deletion applies to storage scripts write, not to a cookie the server sets, so a phone that opens the link three weeks later is still the same participant. The code never has to be typed or shown. What it costs: the trust page's "cookies set by this app: 0" becomes "1, which tells our server which anonymous participant this browser is, and nothing else"; the attribution guarantee is as strong as today. It works in one browser only: the Gmail app's built-in browser and Safari are two browsers on one phone, a cleared browser is a new participant, and a laptop never continues a phone. Opening the email again continues only where it was opened before.

**Forwards, Marco's addition.** Each email carries at its foot a few spare links of the same kind, each with a value of its own, for forwarding. A forwarded spare starts its own participant, so a forward never shares the recipient's cards. The newsletter tool can make the spare values from the recipient's with a suffix, which tells the partner, and nobody else, that two participants came from one email. The in-app invites of the architecture plan become unnecessary; they can stay idle or be retired.

**Decided, 4 November: Path A, with spare links for forwards.** The device-made code stays as the silent fallback nobody sees. The "I have a code" screen goes, and no lifeline link is needed. Path B stays written here as the alternative if the newsletter tool cannot carry a value in a link.

Still to settle with the partner, before Phase 2: which tool sends the newsletter, whether it can put a per-recipient value and a few spares into links, and whether its click tracking keeps the `#` part. One test send answers all three.

## 3. No install offer

Remove the offer and the per-platform steps from the client and the copy. The manifest and the service worker stay: they cost nothing and keep the page working offline for a tab that is reopened. Pull request 42 (a page per workshop and the hand-written worker) existed only to make installs start in the workshop; with no installs offered it is not needed, and the generated worker of ADR 0012 is simpler to keep. **Decided**: closed unmerged on 4 November; the branch stays if ever wanted.

## Tokens: using the smaller models

What has cost the most in this project: sessions that read the whole repository before starting, browser loops with screenshots, the design skills' passes, and many small pull requests each with a full check. A plan for the next weeks:

- **Fable** only where a decision is made or checked: the decision records above, the review of the identity change, and the integrator's merges. Short sessions with a brief, not the builder's work.
- **Opus 5.5** for every builder session. The brief names the files and the done state, and points at the decision record; the builder reads what the brief names, not the repository. Phases 1 and 2 are that kind of work.
- **Sonnet 5.5** for copy and document edits, tests written from a stated behaviour, and the reviewer subagents.
- Habits that save more than the model choice: one pull request per phase, `npm run check` once before opening it, one look in the browser at the end rather than a screenshot per change, no design-skill passes unless a design pass is the task, fresh sessions per brief rather than forks of long ones. This session is the costliest thing running now, because of what it holds; the next step starts fresh with this plan as its brief.
- How it happens without Marco choosing per task: a session that starts a builder names the model in the start call, as the briefs name the files; a subagent for a review or a search is started on Sonnet by the session that needs it. The rule is written here and in the integrator's memory, so every start follows it. Marco's own chat keeps the model he sets for it.
