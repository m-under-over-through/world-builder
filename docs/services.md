# Services

Draft 0.1, 23 October 2026. Companion to the architecture and risk plan.

**The rule.** Free tiers are fine where there is no state and a redeploy takes under an hour. Pay for anything that holds data or that must never pause. Every service below has one owner (you), two-factor authentication on, printed recovery codes with the key envelopes, and an entry in the runbook saying what breaks if it goes away.

## 1. What you already have

**GitHub, free.** Enough. Two changes: create a free GitHub organization for the project instead of using your personal account, so ownership and access are separate from your other work; and split into two repositories. The app repository (client, API, deck engine, deck content, docs) is public, which is what makes the "check the source" claim on the trust page true, and public repositories get branch protection and unlimited CI minutes for free. The ops repository (backup workflow, runbook with vendor specifics, drill scripts) is private, so that a misconfigured job can never print a connection string into a public log. The private repository's nightly backup job uses about 60 of the 2,000 free CI minutes a month.

**Netlify, free.** Right for personal sites and prototypes, not for this. The free plan is single-member and on hobby terms; a site that exceeds its bandwidth allowance is paused rather than billed, and a paused site is the "URL does not work" failure; and it would mix a client project into your personal account. The recommendation is to keep Netlify for your own things and put this project on Cloudflare, which does the static hosting, the API, DNS, the domain and the first backup bucket in one dashboard with no bandwidth cap on static assets. If you would rather stay on Netlify for the static client, open a separate Netlify team on the Pro plan and use it for the client only; the API still has to live elsewhere, so you would be running two vendors where one would do.

## 3. Deliberately not used

- **Analytics, error reporting, session replay** (Google Analytics, Plausible, Sentry, Hotjar). Each one makes the app talk to a third domain and breaks the one-host claim. Aggregate numbers come from your own database; client errors are shown in the diagnostics panel and, if you want them centrally, posted to your own API with no identifying fields.
- **Google Fonts, icon CDNs, script CDNs.** Self-host everything.
- **CAPTCHA.** Friction and a third party. Wave windows, invite links and rate limits do the job.
- **An email-sending service.** The app never emails anyone. Alerts come from the monitor, not from your code.
- **A virtual server you administer.** Patching, disks and reboots are a second job. Managed services only.
- **Netlify Functions for the API.** Workable, but it would spread the project across two vendors and add a database pooler. One vendor for the stateless parts keeps the map legible.

## 4. Account hygiene, once at setup

- Every account under the project organization or a project email, never a personal login.
- Two-factor on everywhere, with an authenticator app, not SMS.
- Recovery codes printed and stored with the key envelopes.
- Billing on one card with alerts on, and the expiry date written in the runbook next to the domain renewal date.
- Vendor logging set to the minimum each allows, and the setting noted on the trust page.
- A page in the runbook per service: what it does, where the login is, what breaks without it, how to move off it.
